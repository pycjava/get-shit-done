<iron_law>
在完成根因调查之前，**禁止修复**。

如果你还没完成 Phase 1，就不能提出修复方案。“快速修一下”不是一个 phase。

**以下红旗一出现就必须停下，按流程走：**
- “先改一下 X 试试能不能好”
- “大概率是 X，我先修这个”
- “我还没完全看懂，但这个可能有用”
- “再试最后一次修复”（尤其已经试了 2 次以上）
- 一次性堆多处改动再跑测试
- 在没有追踪数据流前就开始提方案
</iron_law>

<phase name="1-root-cause">
## Phase 1：根因调查

在进行任何修复尝试之前，先做这些事：

1. **把错误信息完整读完**：包括 stack trace、行号、错误码。很多时候答案就藏在错误信息里。
2. **稳定复现**：你能稳定触发这个问题吗？如果不能，就继续收集信息，不要猜。
3. **检查最近变更**：最近改了什么可能引发这个问题？看 `git diff`、近期提交、新增依赖或配置。
4. **增加诊断性埋点**（多组件系统尤其如此）：先在每个组件边界加日志，确定是**哪里**坏了，再去修**为什么**坏了。
   ```
   对每个组件边界：
     - 记录进入了什么
     - 记录输出了什么
     - 检查每一层的 config / env
   跑一遍 -> 锁定故障层 -> 深挖这一层
   ```
5. **追踪数据流**：坏值最早从哪里来的？沿调用栈逆向往上追，直到找到源头。要修源头，不要只修症状。

**退出条件：** 你能清楚说出：“根因是 X 在 Y 里发生，因为 Z。”
</phase>

<phase name="2-pattern">
## Phase 2：模式分析

1. 在同一代码库里找到相似且正常工作的例子
2. 把参考实现完整读完，不要只扫一眼
3. 列出正常实现与故障实现之间的所有差异，哪怕差异很小
4. 识别所有环境 / 配置 / 依赖层面的假设条件
</phase>

<phase name="3-hypothesis">
## Phase 3：假设与验证

1. 明确写出一个假设：“我认为根因是 X，因为 Y”
2. 做**最小可能改动**来验证它，一次只改一个变量
3. 验证结果：如果有效 -> 进入 Phase 4；如果无效 -> 重新形成新假设。**不要叠加更多修复。**
4. 如果你其实没搞懂，就直接说没搞懂。不要装懂。
</phase>

<phase name="4-implementation">
## Phase 4：实施修复

1. 先创建一个失败的测试用例（或明确的验证命令）
2. 实施**一个**只针对根因的修复，不要“顺手一起改”
3. 验证：测试通过、其他测试没坏、问题真正解决

**如果修复无效：**
- 尝试次数 < 3：回到 Phase 1，用新信息重新分析
- 尝试次数 >= 3：**立刻停下，开始质疑架构。** 未经讨论不要进入第 4 次修复

**架构问题信号：**
- 每修一个点，就在别处暴露新的耦合或共享状态
- 修复必须依赖大规模重构
- 每次修复都会在别处引入新症状

**如果问题在架构：** 先向用户说明，再继续。
</phase>

<apply_in_gsd>
## 在 GSD 执行链中的应用时机

当以下情况出现时，触发这个流程：
- **Rule 1（Bug）**：在“修 bug”前，先完成 Phase 1-3，再动手
- **Rule 2（Missing Critical）**：同样如此，先理解为什么缺失，再补
- **Rule 3（Blocking）**：先把阻塞追到源头，再去解除
- **DEFINE -> VERIFY 步骤中的验证失败**：重试前先触发 Phase 1
- **调用后续修复动作时**：`RETRY` / `DECOMPOSE` 必须建立在 Phase 1-3 的分析上，不能靠猜

**以下理由都不能成为绕过此流程的借口：**
- 修复看起来很 obvious
- 现在时间很紧
- 问题似乎很简单

系统化处理通常比盲改更快。
</apply_in_gsd>
